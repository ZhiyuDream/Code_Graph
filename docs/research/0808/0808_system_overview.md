## 一、整体流程与每步分支

### 阶段 0：离线建图与索引（一次性）

```
llama.cpp 源码
  ↓ tree-sitter 解析（750 文件）
Neo4j 图：Function/Class/File/Directory 节点 + CONTAINS/CALLS 边（26186 条）
  ↓ Louvain 社区发现
196 modules / 1656 concepts（LLM 生成名称和摘要）
  ↓ 两路 embedding 索引
v1：函数名+路径+签名+代码全文截断    v2：函数名+一句职责+签名+代码前 800 字符
```

### 阶段 1：召回（每题一次）

```
中文问题
  ↓ [1a] LLM 关键词抽取（双采样并集 ≤12 个）
  ↓ [1b] 名称索引验证 → LLM 修正一轮（符号假设验证回路）
  ↓ [1c] 三路召回：
      A路 concept-symbol：top-20 concepts（concept 得分=成员函数 sim 取 max）
          → 池内函数按 score = sim + 0.5×symbol_score 重排，取 top-100
      B路 embedding 兜底：纯相似度 top-50
      C路 关键词名称命中（条件注入：仅当池 top-20 与关键词零重合时启用，≤10 个）
  ↓ [1d] RRF 融合 A+B：score(f) = Σ 1/(60+rank+1)
  ↓ [1e] MMR 多样性重排：score/(1+0.5×同目录已选数)
召回池（~150 个候选函数），首屏展示 20 个
  ↓ 附带三张"地图"展示给 Agent：
      关键词命中函数族（按名称前缀分族）
      目录探测（关键词命中密度 Top 目录）
      候选函数签名
```

**分支点**：
- 条件注入触发与否（池子方向已对就不注）——V31 防投毒机制
- 关键词全落空时，验证回路修正也失败 → 召回种子缺失（当前零引用题的主因）

### 阶段 2：ReAct 调查（每题 ≤30 步）

```
每步：
  组装 prompt（问题 + 候选池 + 已读函数/文件状态 + 监督意见 + 近 10 步历史 + skill 策略）
  ↓ LLM 决策（JSON：thought/action/action_input/function_relevance）
  ↓ 分支：
    ├─ LLM 解析失败 → 重试 ×2，仍失败才 finish
    ├─ forced_action 待执行（supervisor 判错后的强制转向）→ 跳过 LLM 直接执行
    ├─ finish 守卫检查：有相关函数没查调用链/有未读调用点线索 → 拒绝一次
    ├─ 分诊安全网：零相关且跳过 ≥3 个候选 → 拒绝 finish 一次
    ├─ 重复动作检测（同 action+参数）→ 拒绝并回放上次结果
    │    第 2 次被拒起 → 升级干预（列出未读调用点清单）
    └─ 正常执行工具
         ├─ read_function（批量 ≤8，observation ≤100k 字符预算）
         │    ├─ 结案文件禁读 → 拒绝
         │    ├─ 记忆缓存命中 → 返回缓存摘录（免读原文）
         │    └─ 正常读完整实现（超大函数只给头部+read_lines 引导）
         ├─ find_callers/find_callees
         │    └─ 命中后系统自动读 top-4 未读调用点实现（确定性扩展）
         ├─ search_symbol（Neo4j 名称索引 + grep 双通道）
         │    └─ 仅在无相关函数时，自动跟进读 top-2 名称匹配函数（条件跟进）
         ├─ list_functions / list_files / read_lines / expand_recall
         ├─ mark_file_irrelevant / skip_candidates
         └─ finish → 出循环
  ↓ 每 5 步：Supervisor 评估方向
      ├─ 正确 → 仅记录
      ├─ 可疑 → 轻量干预：建议关键词重新召回注入池前列（限一次）
      └─ 错误 → 强制转向一次：最近无产出文件结案 + 重新召回 + 下一步系统强制执行
  ↓ 固定步数干预：
      ├─ 第 6/10 步无相关标记 → 方向纠偏提示
      └─ 已有相关 + 连续 4 步无新增 → 提前 finish 提示（只提示不强制）
循环结束（finish 或 30 步上限）
  ↓ 结束前兜底：未读调用点补读 top-3 + 关键词兜底读（未覆盖关键词的名称最匹配 top-1）
```

### 阶段 3：答案生成（每题一次）

```
证据注册表（name@file → 完整代码 + 行号 + 相关性标记）
  ↓ 组装答案 prompt：
      决策日志（非 read 动作保留完整结果）
      + 已读函数清单（含相关性）
      + 相关/未标记函数的完整实现（>30k 字符的头尾保留法）
  ↓ LLM 生成答案
  ↓ 引用自检回路（两级）：
      ① 相关函数所在文件未出现在答案 → 带清单补写一轮
      ② 答案引用了从未读过的文件 → 强制重写（删除或改"无法确认"）
```

### 阶段 4：评估

```
det 确定性核对（主指标）：
  gold 文件 ∈ 答案文本（全路径或 basename，含引用清单）且 ∈ 实际读过集合
llm judge（辅助）：已删除参考答案（防幻觉泄题）+ 举证要求（摘原句）
```

| 013 | 0% | cann/aclnn_ops.cpp | **阶段 1 召回** | 关键词猜错后端（去了 vulkan/cpu） |

| 010 | 50% | ggml-cann.cpp | **阶段 2 调查** | 文件在召回池内，但首屏之后 Agent 没翻到 |
| 034 | 75% | ggml-backend-meta.cpp | **阶段 2 调查** | 工具结果里出现过文件名，Agent 没点进去读 |
| 037 | 50% | arg.cpp | **阶段 2 调查** | 同上——find_callers 结果里出现过但未跟进 |
| 007 | 67% | chat.cpp | **阶段 2 调查** | 调用点枚举不全 |
| 041/042 | 50% | count-equal.cpp/set.cpp | **阶段 2 调查** | 读了相邻文件（set_rows.cpp），漏了目标文件 |

**分布结论**：17 个漏引文件里 **15 个从未进入 Agent 视野**（池内=False 且工具结果没见过）——
阶段 1 召回断链是绝对主导（C 类）；只有 2 个（034/037）是阶段 2 的"看到没读"。

**失明链**（C 类的完整机制）：
```
关键词抽取没猜中核心符号
  → 召回池里没有它的定义
    → Agent 从没读过核心符号
      → find_callers 从没对它执行
        → 它的 call site 永远不会出现在任何工具返回里
          → 未读未引
```
调用链机制只能放大正确的种子，种子缺席时整条链是全黑的。

**系统自动读取**（不计入 Agent 动作）：193 次——自动读调用点/跟进读，是证据的重要来源。

### 关键发现

1. **50/50 全部打满 30 步**：没有一道题提前 finish——"给多少预算吃多少"是硬行为模式，
  提前 finish 软提示只触发 2 次（V45 实验已证明）
2. **finish 拒绝率 96%**：守卫机制几乎每次 finish 都要拦一次——说明 Agent 普遍在
  调用链没查完时就想收工，守卫是必要防线
3. **find_callers 拒绝率 51%**：Agent 对同一函数反复查 callers——
  尽管拒绝时回放了上次结果，它还是会再查一遍。这浪费了约 8% 的步数
4. **expand_recall 几乎不用（4 次）**：召回池翻页机制名存实亡——Agent 宁愿
  search_symbol 也不翻页，池深 100+ 的设计基本没被利用
5. **读取类工具占 54% 的步数**（429+379/1500）：调查是重读驱动，符合设计意图

### 工具层的改进空间（按数据排序）

1. **find_callers 重复调用**（86 次被拒）：拒绝回放后仍重复——可以考虑
  把 callers 结果持久展示在 prompt 状态区（而不是只在 observation 里出现一次）
2. **expand_recall 形同虚设**：召回池翻页和 Agent 心智模型不匹配
3. **list_files 使用率低（16 次）**：目录探索没被用起来，而后端识别题恰恰需要它

## 五、V48：Frontier 账本 + search_codebase（0808 晚）

**动机**（0808 工具分析暴露的两个问题）：
- find_callers 51% 硬拒绝率——调用链结果只在 observation 出现一次，Agent 忘了就重复查
- expand_recall 1500 步只用 4 次——"翻页"不是 Agent 的自然调查动作

**方法**：
1. **Frontier 账本**：每个发现的线索（callers/callees/search/种子）带
   {来源函数、关系、发现步数、why、优先级 HIGH/MEDIUM/LOW} 持久进 frontier，
   prompt 常驻展示【已调查】+【待调查 frontier】；事件日志进结果供漏斗分析
2. **重复 find_callers/callees 首次返回缓存状态**（上次结果+frontier 现状）而非硬拒
3. **search_codebase(query)**：区域级搜索——名称索引命中+目录密度+embedding 重查，
   返回"命中目录+代表函数"结构化报告，结果自动进召回池前列和 frontier

**结果**：
- 子集（12 失败题）：46.5% → 49.3%（+2.8pp）；001 0→33%、042 50→100%
- **全量：det 82.8%（全36/零3）——与 V44 持平（方差带内），零引用 4→3**
- 机制采纳：search_codebase 调用 31 次（expand_recall 同期 2 次）；
  find_callers 硬拒 51% → 30%（首次重复返回缓存）
- frontier 事件日志（每题 30-40 条）已入结果文件，供后续 discovery funnel 分析

**结论**：视野扩展机制被真实采纳且零引用减少，但全量均值仍在方差带。
顽固题（013/032/044）依旧——它们是召回层"无锚"问题，下一轮可做
SkillOpt epoch 或 self-consistency 生产化。

## 六、召回层级测量 + Oracle 粒度实验（0808 深夜，方向性结论）

### 四层召回率（embedding，50 题）

| 层级 | top10 | top50 | top100 | top500 |
|---|---|---|---|---|
| 函数 | 56% | 72% | 84% | 93% |
| 文件 | 84% | 93% | 95% | 98% |
| 目录 | 88% | 95% | 98% | — |

**区域召回远高于函数召回**：系统几乎总能定位到正确的目录/文件，
失败发生在"区域内找函数"这一步。

### Oracle 粒度实验（8 道顽固题，注入 gold 锚点）

| 粒度 | 平均 det | 解读 |
|---|---|---|
| 当前（无注入） | 29.2% | 基线 |
| 函数 oracle | 41.7% | 给了正确函数仍常失败 |
| **文件 oracle** | **62.5%** | **最佳粒度**——整文件上下文让 Agent 自然调查 |
| 目录 oracle | 37.5% | 太宽，噪声淹没 |

逐题亮点：044 文件/目录 oracle 0→100%（函数 oracle 无效——其 gold 函数行归属本身有误）；
031 函数/文件 oracle 0→100%。

**关键反例 013**：文件 oracle 注入了 aclnn_ops.cpp 全部函数，Agent 仍 0%——
池里有正确函数但 Agent 没读 `get_cache_acl_tensor`（首屏 20 个里没它），
转而跑去 vulkan 分析。**这是 Agent 层失败**：文件对了，文件内导航没做
（应 list_functions 扫一遍文件再选目标）。

### 方向性结论

1. **"预测区域，让 Agent 调查"优于"预测函数"**——文件 oracle 显著优于函数 oracle，
  且函数注入有时反而缩窄调查（032 函数 oracle 100→0）
2. Stage 1 应 redesign 为：**问题 → 区域定位（目录/文件级召回 95%+ 可达）
  → 区域内多种子 → Agent 调查**
3. Agent 需要补课的是**文件内导航**：进入正确文件后用 list_functions
  扫全文件函数清单再选目标（013 的教训）
