# 检索与选择分解实验

这些实验将定位问题分解为检索、选择和扩展三个阶段，以确定基于 LLM 的 agent 在哪里丢失了覆盖率。

## 基准

- 数据集：`datasets/benchmark_hard.json`（50 道事后审计问题）
- 仓库：`/data/users/zzy/RUC/llama.cpp`
- 指标：文件级覆盖率，对照 `gold_evidence`（排除 `.h`/`.hpp`）

## 1. 池召回率 vs 选择准确率

我们首先区分两个问题："gold 是否在候选池中？" 和 "LLM 是否选中了 gold？"。

| 阶段 | 完整覆盖率 |
|-------|--------------:|
| 池召回率（gold 文件在 Top20 池中） | ~76% |
| 单符号 LLM 选择 | 52% |
| 多符号 LLM 选择 | 60% |
| Oracle 多符号选择 | 76% |

### 三种"选择"策略的含义

- **单符号 LLM 选择**：LLM 从 Top20 候选池中只选 **1 个**最相关函数/符号。很多问题的 gold evidence 分散在多处，只选 1 个会漏掉其他 gold 文件。
- **多符号 LLM 选择**：LLM 从候选池中选 **多个**相关函数（如 top-3 或开放式多选）。比单选好一些，但仍会漏选部分 gold。
- **Oracle 多符号选择**：假设 LLM 能**完美选中候选池中所有 gold 符号**（理论上限）。它等于池召回率，用来量化选择阶段的损失。

### 这个差异是 prompt 设计导致的

当时的 prompt 明确控制了可选数量：

| 方法 | Prompt 要求 |
|------|------------|
| 单符号选择（`select_best_entry.txt`） | "请从候选文件中选择最可能...的文件。只返回文件路径。" → 强制选 1 个 |
| 多符号选择（`select_multiple_symbols.txt`） | "Select ALL candidate functions... Do NOT limit yourself to one. Select between 1 and 5 candidate IDs." → 允许选 1-5 个 |
| Top-K 选择（`select_top3.txt`） | "Select the TOP {k} functions... Return a JSON array of exactly {k} candidate IDs." → 强制选恰好 k 个 |

**解读：** Top20 池已经包含 76% 问题的 gold 文件，但 LLM 选择只恢复了 52-60%。这最初把问题框定为**选择失败**。

进一步分解：
- 如果 LLM 选择完美 → 覆盖率 76%（即池召回率）。
- 多符号 LLM 选择实际 → 60%。
- 单符号 LLM 选择实际 → 52%。
- 因此**选择阶段的损失约为 16 个百分点**（76% - 60%），而"强制只选一个"又额外损失了 8 个百分点（60% - 52%）。

## 2. Gold 符号在池中的排名

对每道题，我们计算 gold 符号/函数在检索候选池中的排名。

| 统计量 | 数值 |
|-----------|------:|
| gold 排名中位数 | 3 |
| gold 排名 ≤ 5 的比例 | 58% |
| gold 排名 ≤ 10 的比例 | 76% |

大多数 gold 证据在池中的排名其实相当高，LLM 理应能找到。

## 3. Top-K 条件召回

| 条件 | 召回率 |
|-----------|-------:|
| gold 在前 3 名中 | 89.7% |
| gold 与第一名非 gold 成对比较 | 89.7% |

**解读：** 当 gold 处于一个小集合中时，LLM 的识别能力非常好（~90%）。问题不在于 LLM 无法识别证据，而在于 gold 经常不在 LLM 实际查看的小集合中。

## 4. 选择消融与 Prompt 重设计

我们测试了给 LLM 更多上下文是否能提升选择。

| 变体 | 影响 |
|---------|--------|
| 仅签名 | ~0 个百分点 |
| Anchor prompt | +2-4 个百分点 |
| 证据 framing | ~0 个百分点 |

### 这些术语是什么意思

- **仅签名**：给 LLM 看函数名 + 函数签名（参数、返回值），不看函数体。
- **Anchor prompt**：不直接问"哪个函数最相关"，而是问"哪个函数是 **evidence anchor（证据锚点）**"——也就是直接实现或控制问题所问行为的那个函数。这个措辞试图让 LLM 聚焦到"核心实现"而非"相关调用方"。
- **证据 framing**：把选择任务重新表述为"找出能支持或反驳问题判断的证据"，让 LLM 以"证据发现"的视角评估每个候选函数，而不是简单的"相关性打分"。

**解读：** 在选择阶段做 prompt engineering 收益有限，瓶颈不在选择 prompt。

## 5. 成对与锦标赛选择

| 方法 | 召回率 |
|--------|-------:|
| 成对 anchor（gold vs 第一名非 gold） | 89.7% |
| 锦标赛 top-100（5 题） | 80% |
| 锦标赛 top-8（20 题） | 55% |

### 这些术语是什么意思

- **成对 anchor**：不一次性从很多候选里选，而是只给 LLM 看 **2 个函数**：一个是 gold，另一个是排名第一的非 gold。问 LLM"哪个是证据锚点？"。这测试 LLM 在最简单的二选一情况下能不能识别 gold。
- **锦标赛（Tournament）**：不一次性从 N 个候选里选，而是像体育比赛一样两两 PK：
  1. 候选 1 vs 候选 2，LLM 选出胜者；
  2. 胜者 vs 候选 3，再选胜者；
  3. 依此类推，直到比完所有候选。
  这样每步只让 LLM 做二选一，降低认知负荷。
- **锦标赛 top-100**：先检索出 top-100 候选，再在这 100 个里做锦标赛。这个实验只做了 5 题（试点）。
- **锦标赛 top-8**：先检索出 top-8 候选，再在这 8 个里做锦标赛。这个实验做了 20 题。

### 为什么 top-100 比 top-8 好？

看起来反直觉：候选越多应该越难。但原因是：
- 当候选池扩大到 100 时，gold 函数更可能被包含进来（池召回率高）。
- 当候选池只有 8 时，有些题的 gold 根本不在 top-8 里，锦标赛再好也没用。

所以 "top-100 锦标赛 80%" 反映的是"如果 gold 在池里，锦标赛能把它筛出来"；而 "top-8 锦标赛 55%" 反映的是"top-8 池本身经常漏掉 gold"。

**总体解读：** 成对比较有效，因为判别任务容易。但扩展到大的候选池后，纯比较方法的性能会下降——在另一个 Top-N 缩放实验中，条件召回从池大小为 2 时的 94% 降到池大小为 100 时的 74%。

## 6. 命名偏差

选择失败经常与**误导性函数名**相关。LLM 偏好名称与问题关键词匹配的函数，即使实际实现在别处。

## 7. 分解实验的结论

分解实验表明：

1. 检索不完美，但不是唯一问题。
2. LLM 在小集合中能识别证据。
3. LLM 在大候选池中选择失败。
4. Prompt/签名工程无法根本解决。

这引出一个假设：**问题不是选择本身，而是缺乏系统性的收窄/搜索过程**。后续 worklist 实验证实了这一重新框定。
