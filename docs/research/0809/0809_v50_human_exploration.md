# 0809 V50：人类式目录探索 + 调查状态持久化

> 前置阅读：`0809_failure_deep_dive.md`（12 道失败题逐步复盘）。
> 本文档对应代码改动：V50。基线 = earlyfinish 轮（det 84.8%，全 38/部分 9/零 3）。

## 1. 为什么做：复盘发现的六个系统性 gap

0809 复盘对 12 道 det<100% 的题逐步展开轨迹（每题 30 步的输入/输出全看了一遍），核心数字：

- **360 步里 64% 是浪费**：重复动作被拒 30% + "记忆命中"重读 23% + 空搜索（符号不存在）11%。
- **12/12 题都存在一个"一步之遥"动作**：做了就大概率拿到漏引文件，且所需线索全部已在工具结果里出现过（find_callers 列表、find_callees 列表、grep 文件清单、初始召回池前列）。
- 两个工程 bug 直接丢分：析构函数 `~xxx` 永远读不到（001/034）；监督者每题幻觉 3-4 个不存在的符号（全部 12 题）。

用户方向性判断（本轮改进的出发点）：**初始召回池不应该决定一切**。Agent 应该像人类工程师一样：
1. 觉得某个目录大概率有相关文件 → 先扫一眼；
2. 扫完不相关 → 记住结论，换别的目录，不回头；
3. 找到很相关的文件 → 顺藤摸瓜看同目录的文件、文件内的函数、调用/依赖链；
4. 召回仍按函数粒度为主；函数粒度没锚点时（问题无明确符号），走"目录粗筛 → 精读"的降级路径。

## 2. 方法：六项改动

### 改动 1：修析构函数读取 bug（工具层）

**解决什么问题**：001/034 两题的 gold 调用点是析构函数（`~ggml_cann_pool_buf`、`~ggml_backend_meta_context`），`read_function` 对它们永远返回 "function not found in this file"；更糟的是"升级干预"机制把这两个永远读不到的函数列为强制待读项反复推送，形成死锁（001 烧掉 12 步）。

**根因**：`src/qa/tools/grep_call_chain.py` 的 `read_function` 用 `\b{name}\s*\(` 匹配定义行。`\b` 是单词边界，而 `~` 不是单词字符——空格和 `~` 之间不存在单词边界，正则永远匹配不到。

**改法**（两处）：
- `\b` 换成负向后行断言 `(?<![A-Za-z0-9_])`，对 `~dtor`、`operator==` 等非单词字符开头的名字都能匹配；
- 正则扫描仍失败时，用 Neo4j tree-sitter 行号表兜底（`MATCH (f:Function {file_path}) WHERE f.name = ... OR f.name ENDS WITH ...` 拿到精确 start/end 行，直接切区间）。

**验证**：`~ggml_cann_pool_buf`（450-463 行）和 `~ggml_backend_meta_context`（1497-1507 行）均可读出；普通函数回归正常。

### 改动 2：新增 `scan_directory` 工具（目录粗筛）

**解决什么问题**：013（进了 ggml-cann 目录没进 aclnn_ops.cpp）、041/042（在 ggml-sycl 主文件打转，不知道同目录还有 76 个算子文件）。Agent 此前只有 `list_files`（只给文件名）和 `list_functions`（单文件函数清单），没有"快速扫一个目录大概有什么"的能力。

**改法**：`src/qa/tools/react_tools.py` 新增 `tool_scan_directory(directory)`：列出目录下代码文件 + 每个文件的函数名清单（Neo4j 索引，一次 cypher 查询，**不读任何文件内容**，成本极低）。上限 12 文件 × 15 函数名。Agent 侧包装时标注每个文件的状态（含相关函数/已结案不相关/已读 N 函数）。

定位：**"粗筛再精读"的粗筛环节**——用户指定的无锚问题降级路径的关键工具。

### 改动 3：目录账本（人类式目录记忆）

**解决什么问题**：人类工程师会记住"前面看的目录大概是怎么回事"，Agent 之前没有这个状态——看过的目录、得出的结论滑出上下文就丢了，导致重复探索或在错误区域打转（044 在 ai_chat.cpp 打转 30 步）。

**改法**：ReactAgent 新增 `_dir_ledger_text()`，每步从 `read_functions`/`file_status`/`visited_functions` 推导，prompt 新增【目录调查状态】段：

```
- ggml/src/ggml-cann/ 相关: ggml-cann.cpp；未探索 5 个: acl_tensor.cpp, aclnn_ops.cpp, ...
- vendor/miniaudio/ 不相关: miniaudio.h 【已排除，勿回头】
```

配套：**同目录 sibling 提示**——某文件新被标记为相关时，observation 附带"该目录下还有 X 个未探索文件：...（相关文件的邻居常常也相关）"，每目录只提示一次。这就是"顺藤摸瓜看同目录"的机制化。

### 改动 4：已读摘要 + 重读回放（治 64% 浪费的大头）

**解决什么问题**：010/013/037/044 的主死因——历史窗口只保留最近 ~10 步的动作签名（不含 observation 内容），旧内容滑出后 Agent 认为"没读过"，于是重读 → 精确去重 guard 拒绝 → 换参数写法（file_path/file_paths、行号区间微调）绕过 guard 重读成功（记忆命中）→ 再滑出再重读。037 把同一个 25 行的函数读了 10 遍，最后还在答案里说"无法从实现级别确认"。

**改法**（两条腿）：
- **已读摘要进账本**：【调查账本·已调查】每行从 `- name（相关，callers✓）` 扩展为 `- name（相关，callers✓）— void ggml_cann_set_device(const int32_t device) {`（签名首行作为职责提示）。Agent 每步都能看到"我读过什么、它大概是什么"。
- **重读回放不拒绝**：read_function/read_lines 的重复调用（包括参数换皮的模糊重复——目标函数全部已在证据注册表）不再拒绝，直接从注册表/磁盘回放完整内容，标注【回放：你之前读过】，不计重复拒绝、不触发升级干预。Agent 的信息需求被满足，循环自然终止。

### 改动 5：监督者建议符号的存在性过滤

**解决什么问题**：监督者每题建议 3-4 个仓库里不存在的符号（`switch_device`/`find_template`/`check_jinja_template`/`enqueue_set`...），Agent 老实执行搜索全部空手（12 题共 40 步空搜索），重复搜索再被 guard 拒绝，雪上加霜。

**改法**：`_call_supervisor` 拿到 `suggest_keywords` 后，先过全量函数名索引（一次性构建小写 blob，子串匹配，毫秒级），不存在的剔除，并在注入的 guidance 里如实注明"监督者建议的 X/Y 在符号索引中不存在，已忽略，请勿搜索"。副作用收益：监督者判"错误"时的强制转向动作（search_symbol(第一个关键词)）和重新召回，现在只用真实存在的符号。

### 改动 6：finish 守卫 / 升级干预的推送清单过滤

**解决什么问题**：007 的 finish 守卫要求对**测试函数**补 find_callers（对"生产调用方契约"问题没有证据价值）；001/034 的升级干预强推**不可读的析构函数**（配合改动 1 已修可读性，此处再加一道保险）。

**改法**：`_unread_leads()` 和 finish 守卫 B 的 `pending_chain` 都排除 `tests/` 目录下的函数。

### Prompt 更新（prompts/react_investigation.txt）

- 工具列表加 `scan_directory`（第 5 号），说明其"粗筛"定位和成本优势；
- 新增【目录调查状态】段；
- 新增"调查策略"五条（人类式探索）：召回池只是入口不是世界的全部 / 找到相关文件顺藤摸瓜 / 工具结果里的陌生符号名就是线索 / 排除要果断不回头 / 向下追溯值的来源；
- 已调查账本说明改为"每行附职责摘要；确实忘记细节可以直接重读，系统会回放"。

### 4.2 V50 暴露的新问题：监督者"重读指令"空转（044 案例）

044 在 V50 里出现了新的病态循环：step 11-23 **连续 13 次 read_lines 同一区间（ai_chat.cpp:76-105）**。每次回放都正常返回了内容，Agent 的 thought 却始终是"监督者要求精确重读 76-105 行"——**循环的驱动者不是上下文丢失，而是监督者**。监督者每 5 步看一次"最近 5 步动作摘要"，发现分析没推进，就继续下令"重读 init_context 完整函数体"；Agent 把监督指令当命令服从，回放机制反而让这个动作永远"成功"，永远不会被打断。

### 4.3 V51 修正（在 V50 基础上叠加）

1. **回放上限**：同一内容（read_function 按目标函数集合、read_lines 按文件+区间做指纹）回放 2 次后，第 3 次起转为硬拒绝："这已经是你第 N 次读取完全相同的内容，内容不会有任何变化。请直接基于已读内容给出分析结论，或转向全新方向。"并计入升级干预（让它推送其他未读线索）。
2. **监督者 prompt 加约束**（`prompts/react_supervisor.txt`）：
   - 绝对不要要求 Agent 重读已读过的函数/区间；
   - Agent 已读核心函数但分析没推进时，指令应是"基于已读代码给出结论"或"finish 写答案"，或指出一个具体的未读新对象；
   - Agent 连续多步在同一文件重复动作时，指令它换明确不同的方向，而不是"再读一次"。

### 4.5 V51 冒烟暴露的最后一个系统性盲区：callee 归属文件错误

002/014/037 的轨迹分析发现它们卡在同一个地方：Agent 对核心函数做了 `find_callees`，callee 列表里**出现了** gold 符号（`llama_model_chat_template`），frontier 也记了它——**但文件归属记错了**。`grep_callees` 只能给出被调函数的名字，给不了定义文件，旧代码直接 `c.get("file", file_path)` 把 callee 记到**当前文件**（chat.cpp）头上。Agent 按错文件去读 → 读不到 → 线索烂在 frontier 里。这解释了为什么"一步之遥"动作在这些题里一直没发生：不是 Agent 不想跟，是 frontier 给的地址是错的。

**V52 改动**：find_callees 的 callee 进 frontier 前，先用名称索引解析真实定义文件（已读注册表 → func_file_map → chunks_by_id 精确匹配，优先 .cpp 实现文件）；解析到跨文件 callee 时，在 observation 里明示"【跨文件被调方】以下被调函数定义在其他文件"。

**V52 验证**：直接跑全量（冒烟子集在 V50/V51 已验过两轮机制有效性，V52 是单点修复）。

### 5.3 回退逐题归因（读了 V51 全量轨迹）

- **031（100→0%）**：召回运气 + 错锚定。gold 是 `ggml_backend_cann_init`，在池内第 20 名（score 0.011，池尾）；virtgpu 的 `apir_*` 函数占了池前列（rank 1/5/9/15/16/18）。基线轮 Agent 读了池尾这个 gold（运气），V51 轮 Agent 在 ggml-virtgpu 深挖 30 步没出来。它把 virtgpu 函数标了相关（它们确实是"后端初始化"，只是不是题目要的 CANN），所以"无相关函数"方向纠偏提示不触发。**不是 V51 机制打坏的，是 C 类锚定问题的方差显形。**
- **021（100→0%）**：同上，召回方差 + 错目标 latch。基线池内 gold 排 1/4/7/9/12，V51 轮排到 9/13/14/17/19（关键词抽取是 LLM 做的，两轮抽的词不同），Agent 前期 latch 到 `common_params_parser_init` 等错误目标反复回放，gold 函数的读取调用给错了文件路径（read 失败，但 function_relevance 里标了相关，造成"读了"的假象）。
- **011（100→67%）**：speculative.cpp 进了 visited（工具结果出现过）但没读没引——差一步。
- **012（100→67%）**：common.cpp 在答案里引用了但没读过，det 判"编造型引用"不计——这其实是 det 口径的诚实性在起作用。

### 5.4 结论

- V50-V51 的机制在失败子集上是强净收益（+18.8pp，0 回退），全量上被 4 题回退抵消成 -1.2pp。
- 4 题回退里 2 题（021/031）的主因是**召回/锚定的运行间方差**（同一套召回代码，LLM 抽关键词不同 → 池子排名不同 → 锚定成败不同），不是新机制打坏的；2 题（011/012）是"读过没引/引了没读"的一步之遥。
- 待验证：V52（callee 归属修复）全量。若 V52 全量 ≥ 基线 84.8%，则定稿；若 021/031 类题继续波动，说明需要专门处理"池尾 gold 可见性"或接受该方差。

## 7. V53：失败边界漏斗 + 文件内导航 ablation

### 7.1 漏斗分析（动机与方法）

用户提出：既然区域定位已经做进系统，下一步应该回答"**Agent 已经能拿到正确文件/区域之后，为什么还是不能稳定地把文件里的正确证据找出来**"。方法：对 V52 全量里每个漏引 gold 文件，逐阶段检查存活（工具：`scripts/analysis/funnel_analysis.py`，纯轨迹统计，零 LLM 成本）：

```
gold 在初始召回池 → 文件名出现在任何工具结果 → 对该文件/目录做过 list_functions/scan_directory
→ gold 函数名出现在 observation → 真正读过 → 标记相关 → 最终引用
```

### 7.2 漏斗结果（13 个漏引文件样本）

| 阶段 | 存活 |
|---|---|
| 在初始召回池 | 2/13 |
| 文件名出现在工具结果 | 7/13 |
| **list_functions/扫目录过该文件** | **1/13** |
| gold 函数名出现在 observation | 7/10 |
| **真正读过** | **0/13** |
| 标记相关 | 0/13 |

**断点结论：不在"找到文件"，在"进入文件后的结构化导航"**——Agent 几乎从不枚举自己在看的文件（1/13），gold 函数名大多在眼前出现过（7/10）但没有一个被真正读（0/13）。

### 7.4 ablation 结论

1. **044：oracle 文件注入 → 0→100%（B/C 都是）**。纯召回/锚定题：正确文件的函数进了池子，Agent 自己就能完成全部调查。实锤"不是调查能力问题"。
2. **013：四组全部 0%——连 oracle 文件注入 + 强制函数清单都救不回来**。逐帧看 C 组轨迹：oracle 把 aclnn_ops.cpp 的函数注到了池子 rank 1-8（`bcast_shape`/`aclnn_add` 等），gold 函数 `get_cache_acl_tensor` 在 rank 39；Agent **一个都没读**，全程在 `llama-kv-cache.h` 的 `resize` 上空转。原因：**名字语义带偏**——问题的"缓存扩容"在代码里的主导概念是 KV cache（`llama-kv-cache` 一票函数名字更匹配），而 gold 函数名 `get_cache_acl_tensor` 看起来像"获取 tensor"，不像扩容。Agent 按名字相关性选目标，被 KV-cache 方向吸走。File Map 也没触发——因为它从没读过 aclnn_ops.cpp 的任何函数（读了才附清单）。**这是"名字消歧"失败，不是导航失败**；013 的修复方向是召回侧/选择侧（比如"池中同一文件聚簇的信号"或"名字看似无关但所属文件聚簇的函数也要抽查"），不是再加导航机制。
3. **D 组（无 oracle，纯 file-recon）：+16.7pp（40.9→57.6%），4 升 0 降，token 成本 ±0%**（312k→311k/题）。037（arg.cpp）、027、010 直接满分。这是可上线的净收益。
4. C 组全引用数最高（5/11）但平均分和 B 持平——oracle 池子已经把正确函数摆出来了，recon 的增量主要发生在"进入的文件不在池子里"的场景（D 组证明了这个场景真实存在）。

### 7.6 V53 全量第一次：82.0%（-5.0pp vs V52）——方差还是回退？

V53（file-recon 默认开）全量第一次：82.0%，零引用升到 6 题（021/032/036/001/013/044）。但逐题分解后发现**不是 file-recon 打坏的**：

- 新增的零引用题（021/032/036/001）**File Map 全部只触发 0-1 次**，且失败模式都是老问题：召回锚定错区 + 单文件 read_lines 重读循环（032 在 backend-reg.cpp 读 15 次、036 在 ngram-cache.cpp 读 17 次——036 是 `ngram-map` vs `ngram-cache` 的名字撞车锚错文件）。
- **决定性证据**：按 File Map 是否触发的分组对比——触发组（20 题）85.8%→83.3%，**未触发组（30 题）87.8%→81.1%**。未触发组机制和 V52 完全同构（File Map 从未出现），降得反而更多 → 说明本轮下跌的主体是运行间方差，不是 file-recon。
- 014（V52 刚修到 100%）本轮 67%，File Map 未触发——同样的题同样机制两轮差 33pp，再次印证方差量级。

**处置**：V53 全量跑第二次估方差。若第二次回到 85%+，则 82.0% 是倒霉 roll，file-recon 照常上线（D 组对照实验 +16.7pp 0 回退是同 run 配对比较，证据强度高于全量单跑）。

**方法论教训（重要，写给后续所有实验）**：deepseek-v4-flash + LLM 关键词抽取的组合下，单题两轮可以 100↔0 摆动（021 四轮成绩 100/0/100/0），全量平均方差 ±3-5pp。**任何改动用全量单跑做裁判都不可靠；有效裁判只有两种：① 同 run 配对子集对照（如 D vs A）；② 全量跑 2 次取平均。** 之前 V51 全量 83.7% 被判"-1.2pp 回退"、V52 被判"+2.2pp"，回头看都在方差带内——真正可信的信号只有失败子集的同 run 对照（+18.8pp）。

### 8.2 新发现的 4 个 bug（已全部修复）

**Bug 1：监督者输出非 dict 时静默丢弃（影响面最大）**
`_call_supervisor` 里 `call_llm_json` 对"合法 JSON 但非 dict"（如 LLM 把答案包成数组 `[{...}]`）的返回，`json.loads` 能解析成功 → 返回 list → 监督者 `isinstance(note, dict)` 检查直接 return——**无日志、无重试、无记录**。V53-r1 里多数题只有 3-4 次监督记录（应为 5 次），044 只有 1 次。044 的重读确认循环本来指望 V51 的监督 prompt 约束来打断，结果监督根本没上班。
**修复**：`src/core/llm_client.py` 的 `_try_parse` 只接受 dict（数组/字符串落到 repair/None 路径）；`_call_supervisor` 丢弃时打 `[SUPERVISOR_WARN]` 日志。

**Bug 2：scan_directory 按字母序截断，大目录里 relevant 文件被切掉**
common/ 有 51 个代码文件，`max_files=12` + 字母序 → 只显示 arg.cpp 开头的 12 个。036 的 gold `ngram-map.cpp` 就在被切掉的 39 个里，Agent 扫了目录却永远看不到它。
**修复**：`tool_scan_directory` 加 `keywords` 参数，按"文件名/函数名命中关键词数"降序排列再截断（Agent 侧传 `keyword_hints`）。验证：`scan_directory("common", keywords=["ngram",...])` 现在 ngram-cache/ngram-map 排最前。

**Bug 3：V52 callee 归属解析对泛名误配**
`find_callees(~ggml_backend_registry)` 返回 `release`（来自 `entry.handle.release()`），V52 的归属解析把它"精确"解析到了 `tools/server/server-context.cpp` 的某个 `release`——跨文件线索表里出现完全无关的条目，污染 frontier。
**修复**：`_resolve_symbol_file` 加泛名 blocklist（release/get/find/empty/lock/size/max/min/end/begin/push_back/...）+ 长度 <4 不解析。

**Bug 4：read_lines 换皮区间重读无防护**
回放去重只认精确参数（file,start,end），Agent 微调区间（1-114 → 1-120 → 1-250 → 1-260 → 1-300）就能无限重读同一内容：032 对 backend-reg.cpp 头部读了 7 次，036 对 ngram-cache.cpp 读了 17 次。
**修复**：`file_line_ranges` 记录每个文件已读区间，新请求区间 ≥80% 被覆盖 → 按重复处理（回放）。

### 8.3 方差量化（重要方法论数据）

V53 同代码两轮全量：82.0% / 82.8%（聚合稳），但**逐题平均差 11.8pp，10 题摆动 >30pp**（001/002/007/012/014/021/031/036/037/042）。聚合指标方差 ±2-3pp，单题方差极大。

**裁判规则（更新）**：
- 全量单跑比较 <3pp 的差异：不可归因；
- 全量双跑平均比较：可判 ~2pp 以上差异；
- 同 run 配对子集对照（如 ablation D vs A）：最可信，优先使用。

### 8.4 file-recon 的去留

- 支持上线：D 组同 run 对照 +16.7pp、4 升 0 降、token ±0%；
- 疑似回退：V53 两轮全量均值 82.4% vs V52 单轮 87.0%；
- 待裁决：V52 全量第二次（进行中）。若 V52-r2 也在 82-84%，则 V52≈V53≈85±3%，file-recon 按 D 组证据上线；若 V52-r2 回到 86%+，则 file-recon 在全量上可能真有副作用（File Map 打断调用链深挖？），需要收窄触发条件（比如只在"该文件函数数 ≥10 且当前无相关函数"时触发）。

### 8.5 截断/格式专项审计（用户专项要求）与修复

用户警示：起手代码有 bug 但表面看着没问题，会污染"方法有没有用"的判断。对整条数据通路做截断点审计，又发现 3 个静默截断（均已修复）：

**Bug 5：记忆摘录把片段标成"完整阅读"（证据污染）**
`FunctionMemory.note_read` 只存 `code[:1500]`，但命中回放时写"来自此前调查的**完整阅读**，可直接引用"，且这段 1500 字符的摘录会作为 "code" 进入答案证据注册表——Agent 和答案生成器都拿着片段以为是全文。长函数（>1500 字符）的证据完整性被静默破坏。
**修复**：note_read 记录 `truncated` 标记；命中回放只允许完整条目，长函数落到真实重读。旧缓存无标记的按"摘录满 1500 字符即截断"兜底。

**Bug 6：find_callers 静默截断在 10 处还报"找到 10 处"**
`grep_callers` 链路双重 cap（grep 文件列表 cap 20、调用点 cap 10），工具输出"找到 10 处对 X 的调用"——**对"调用方契约"类问题（benchmark 主力题型），Agent 会把截断结果当成全部调用方下结论**。
**修复**：cap 提到 25，多查 1 个检测溢出，溢出时明示"超过上限，仅显示前 25 处，这不是全部调用方"。find_callees 同款修复（15 + 溢出声明）。

**Bug 7：det 评估 basename 子串误配**
`common.cpp` 会命中答案里的 `server-common.cpp`（012 案例：没读过 common.cpp 却被判"编造型引用"，名义上还是"引了"）。
**修复**：basename 匹配加 `[A-Za-z0-9_\-.]` 边界。**注意：修复后历史轮次数字有小幅平移**（如 V53-r1 82.0%→81.3%），本文档 8.6 起全部使用修正后口径（`_det2.json`）。
