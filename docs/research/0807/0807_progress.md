## 实验二：跨题 Memory（#6，负结果）

**思路**：把每次调查的函数相关性判定存入
`data/investigation_memory.json`，后续问题的候选列表标注"历史:相关×N"——
人类审计员看到老面孔会立刻想起上次结论。

**实现**：`src/qa/memory.py` + Agent 集成（`--memory` 开关）。

**结果（7 题两遍）**：pass1 67.9% → pass2 **47.6%（-20pp，更差）**。
001/002 从 67% 跌到 0。**失败原因**：历史"相关"标记把 Agent 锚定到上一题的
方向上，不同问题的"相关"含义不同，跨题复用变成错误强化。
**结论：关闭**（机制保留在 `--memory` 开关后，默认不启用）。
这正是"机制只在需要时触发"原则的反向印证——记忆没有区分"何时该用"。

## 实验二 b：Memory v2 —— 函数知识缓存（修正方向后有效但温和）

**修正**（用户指出）：记忆的对象应该是**函数本身的知识**（它做什么、代码结构），
而不是"对上一题相关吗"——后者是问题绑定的，前者是问题无关的资产。

**实现**：`src/qa/memory.py`（FunctionMemory）。真实读过完整实现才写入缓存
（职责一句话 + 代码摘录 1500 字符 + 行号）；后续调查 read_function 命中缓存 →
返回缓存摘录免重读（可引用）；需要细节时 Agent 可 read_lines 深挖。
基底为全量 function_summaries.json（展示增强用，不参与免读）。

**子集（7 题两遍）**：66.7% → 81.0%（+14.3pp，含顺序混淆）。
**全量（50 题两遍）**：

| | pass1 | pass2 | Δ |
|---|---|---|---|
| det 覆盖 | 82.5% | 84.0% | +1.5pp |
| 全引用 | 37 | 36 | -1 |
| 零引用 | 5 | 3 | **-2** |
| token | 12.0M | 12.0M | +1.3% |
| 记忆命中 | — | 1094 次 | — |

**结论**：方向正确（v1 负 → v2 正），但全量效果温和（噪声带上沿）；
token 中性——省 token 的上限在"少跑步骤"而非"读得更短"。
**v1 与 v2 的对照是本次最有价值的结论：记忆函数知识 √，记忆问题判定 ×**。

## 实验四：V49 文件中心调查（redesign 尝试，全量回退）

**背景**：四层召回测量显示区域召回远高于函数召回（目录 top50 95% vs 函数 72%），
Oracle 粒度实验显示文件 oracle（62.5%）> 函数 oracle（41.7%）——
"预测区域让 Agent 调查"在理论上优于"预测函数"。

**V49 实现**：Stage 1 改为输出 top-8 文件（File Profile embedding +
函数聚合 RRF 融合）+ 每个文件的 File Map（完整函数清单）+
进入文件自动侦察（首次读文件附全文件函数清单）。

**结果**：
- 子集（12 失败题）：46.5% → 45.1%（持平）；001 修好（0→67%）
- **全量：det 75.8%（全33/零7）——明确回退，跌出方差带**

**失败根因**：实现把召回池**替换**成了 top 文件的函数。大幅下滑的题
（018/032/038 全部 100→0）池子里只剩 1 个文件——top 文件猜错时
Agent 没有任何备选方向。所有既有机制的前提是"视野内什么都有"，
收窄视野的 redesign 违反了系统赖以工作的假设。

**教训**：
1. 区域导航信息应该以**附加**形式回归（File Map 作为额外展示），
   而不是替换函数池
2. 任何收窄视野的改动必须全量验证——子集暴露不了这种伤害
   （子集持平，全量 -7pp）
3. 区域>函数的检索结论本身依然成立，等待正确的集成方式

**当前正式版**：V44 配置（file-centric 默认关闭）。

## 实验三：提前 finish 提示（省 token 尝试，失败但无害）

**动机**：30 步预算必定占满（"给高预算就必定占满"），token ≈ 步数 × 每步大小，
缓存只能提质不能减量，省 token 必须让简单题早收工。

**机制**：已有相关函数且连续 4 步无新增相关 → 注入提示"证据可能已足够，
请盘点后直接 finish"（只提示不强制，手无相关的题永远不提示，防漏证据）。

**全量结果**：det **84.8%（无损失，噪声带上沿最高）**，但**提示只触发 2 次**，
全部 50 题依然打满 30 步（min=中位=max=30），token 12.0M→12.2M。

**失败原因**：LLM 几乎每步都会标点什么为相关，"4 步无新增相关"几乎不成立——
软约束改变不了"填满预算"的行为胃口。
**结论**：省 token 只能靠硬机制（质量分识别简单题砍预算，或直接砍 max_steps），
提示类机制无效。本条线给出明确结论。
